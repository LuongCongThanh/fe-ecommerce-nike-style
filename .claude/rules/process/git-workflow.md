# Git and Pull Request conventions

## Permission to act

- Never create/switch a branch, commit, amend, rebase, merge, push, open a PR, or change a GitHub Issue unless the user explicitly requested that specific action.
- Read-only commands like `git status`, `git diff`, `git log`, `git show`, `git branch --show-current` are fine for understanding repository state.
- Do not infer that "task done" means "commit" or "push".
- Before any Git mutation, read `git status --short` and confirm the current branch.

## Protecting the user's worktree

- Every existing or untracked file is treated as the user's until proven to belong to the current task.
- Do not use `git reset --hard`, `git checkout -- <file>`, `git restore <file>`, `git clean -fd`, stash, or delete a branch to clean up the worktree unless the user asked for exactly that operation.
- Do not overwrite, format, or stage a file outside scope just to make `git status` look clean.
- If the task's changes overlap with pre-existing changes, stop and report the specific conflict; do not silently pick a version.
- Do not use `git add .` or `git add -A` by default. Stage specific paths after reviewing the diff.
- After staging, check `git diff --cached --check` and `git diff --cached` before committing.

## Branch model

```text
main  <- release PR from dev
dev   <- integration/default branch
<type>/<issue-number>-<slug> <- feature/fix/docs branch from dev
```

- Regular branches are created from `dev`, not from `main`.
- Branch names use lowercase kebab-case: `feat/42-product-filter`, `fix/57-cart-quantity`, `docs/12-agent-conventions`.
- `<type>` must match the main intent and a Conventional Commit type: `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `ci`, `perf`, `style`, `build`, `revert`.
- One branch addresses one focused issue/slice. Do not bundle in unrelated refactoring or cleanup.
- Never push directly to `main` or `dev` unless the user explicitly says so and repository policy allows it.
- No force-push. Never use `--force`; `--force-with-lease` also needs an explicit request since it still rewrites remote history.

## Commit

Format:

```text
<type>(<scope>): <imperative summary>
```

Examples:

```text
feat(storefront): add catalog gender filter
fix(admin): preserve inventory form values on conflict
refactor(api-sdk): centralize error envelope parsing
docs(agents): define git workflow conventions
test(schemas): cover invalid order transitions
```

- The summary is imperative, specific, with no trailing period; keep it to roughly 72 characters when reasonable.
- Scope is the affected app/package/domain (`storefront`, `admin`, `cms`, `api-sdk`, `schemas`, `ui`, `agents`); omit it if the change genuinely spans the repo.
- Commits must be atomic: one behavior/refactor/docs unit that can be reviewed and reverted independently.
- Do not mix repo-wide formatting, generated output, or an unrelated dependency bump into a feature commit.
- Add a body only to explain the "why", a constraint, a migration, or breaking behavior; do not re-list the diff.
- A breaking change uses `!` and a `BREAKING CHANGE:` footer when the public contract truly changes.
- Commit messages must never contain the name of an AI tool, model, coding agent or assistant, including but not limited to: Claude, Anthropic, Codex, OpenAI, ChatGPT, Copilot, Gemini, Cursor, Windsurf, Perplexity, DeepSeek, Qwen, Grok, Llama and Mistral.
- Never add `Co-Authored-By`, `Generated-By`, `Assisted-By`, or any direct/indirect AI attribution. No euphemisms like "AI-generated", "generated by an assistant", or "agent-assisted".
- The `.husky/commit-msg` hook enforces a list of common names; this convention still applies to any other agent name not yet covered by that regex.
- Never use `--no-verify` to skip the hook. If the hook is wrong, fix the cause or report the blocker.
- Do not amend the user's commit unless asked. When asked to amend, confirm the current commit belongs to this task and has not been shared unexpectedly.

## Staging and generated files

- Review `git diff -- <paths>` before staging each related group of files.
- Stage source and tests that belong to the same behavior. Docs/contract changes for the same slice are staged together when needed so the commit is self-contained.
- Never stage secrets, `.env.local`, credentials, tokens, build output, coverage, `.next`, `dist`, logs, or scratch files.
- A generated file is only committed if the repository tracks it and the workflow requires it. Do not hand-edit `apps/*/src/routeTree.gen.ts`; run the file's owning generator/build step.
- A lockfile only changes alongside its package manifest and must reflect the actual package-manager command run. Never hand-edit a lockfile.
- If a formatter changes a file outside scope, revert just that formatting with a safe edit; never use a destructive restore command on a file that has the user's changes.

## Pre-commit checks

The `.husky/pre-commit` hook already runs `lint-staged` (Prettier on staged files), `pnpm lint`, `pnpm typecheck` and `pnpm build` (turbo, cached) on every commit and blocks it on failure. That covers formatting, linting, type safety and the build — it does not run tests. Before committing:

1. `git status --short` — scope is correct, no stray files.
2. `git diff --check` — no whitespace errors/conflict markers.
3. Run the focused test for the changed behavior (the hook does not do this).
4. Review `git diff` for debug code, secrets, vague TODOs, generated noise, and out-of-scope changes.
5. Stage specific paths; re-review `git diff --cached`.

Do not treat a hook failure as something to bypass; fix the underlying lint/type/build error. Never claim a commit is "fully checked" while a gate was skipped; state clearly which gate was skipped and why.

## Rebase and merge

- Feature branch into `dev`: prefer squash merge per `CONTRIBUTING.md`.
- `dev` into `main`: the release PR uses a regular merge to preserve the already-squashed feature commits.
- Do not merge `main` back into a feature branch just to "update" it if the workflow uses rebase; pick the strategy per the user's/repository's request and do not mix both arbitrarily.
- Before rebasing, make sure the worktree is clean, or have a plan — with the user's agreement — to protect existing changes.
- When resolving a conflict, read both sides and the related contract; do not blanket-pick `ours`/`theirs` for an entire file.
- After a rebase/conflict resolution, rerun the relevant tests and confirm no `<<<<<<<`, `=======`, `>>>>>>>` markers remain.

## Pull Request

- Feature/fix PRs target `dev`; only a release PR from `dev` targets `main`.
- The PR title follows Conventional Commits and reflects the main change.
- Use `.github/PULL_REQUEST_TEMPLATE.md`; fill in Summary, Test plan, and Related issue.
- Link the issue with `Refs #N`; use `Closes #N` only when the merge should genuinely auto-close the issue per the workflow.
- The PR description states the behavior, key decisions/constraints, how it was tested, screenshots for UI changes, and risks/migration if any.
- The PR title/body must never contain the name of an AI tool, model, agent or assistant, and must never carry AI attribution in any form; CI checks against a list of common names.
- Issue comments, PR comments, review comments, review summaries, release notes and GitHub discussions must also never mention an agent/assistant or describe content as AI-generated. Describe only the technical change, the decisions, the test evidence, and the actual person responsible.
- A PR must be small, focused and reviewable. If a diff bundles several independent concerns, split it into separate branches/PRs before opening.
- Never self-merge. Only merge when the user asks, CI is green, and the target/strategy is correct.

## Issue and traceability

- The issue/PRD is the source of the delivery scope. Do not silently expand the acceptance criteria.
- Branch, commit, and PR should share the same issue/domain vocabulary where possible.
- Triage uses one matching label: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`.
- The type label must match the kind of change (`type:feat`, `type:fix`, `type:docs`, ...).
- Do not change labels, close/reopen an issue, or edit a milestone unless asked.

## Safe recovery

- A wrong commit that hasn't been pushed: report the diff and propose a fix; do not auto-reset/amend.
- A commit that has been pushed: prefer a corrective/revert commit with a clear history; do not rewrite history without agreement.
- Wrongly staged files: unstage without losing working-tree changes, and only after confirming the correct paths.
- Before any operation that could lose data or rewrite history, state exactly which commit/branch/file is affected and wait for confirmation.
