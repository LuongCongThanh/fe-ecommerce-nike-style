# Convention Git và Pull Request

## Quyền thực hiện

- Không tạo/switch branch, commit, amend, rebase, merge, push, mở PR hoặc thay đổi GitHub Issue nếu người dùng chưa yêu cầu rõ hành động đó.
- Lệnh read-only như `git status`, `git diff`, `git log`, `git show`, `git branch --show-current` được phép dùng để hiểu trạng thái repository.
- Không suy diễn “hoàn tất task” đồng nghĩa với commit hoặc push.
- Trước mọi mutation Git, đọc `git status --short` và xác nhận branch hiện tại.

## Bảo vệ worktree của người dùng

- Mọi thay đổi có sẵn hoặc untracked file đều được coi là của người dùng cho tới khi chứng minh thuộc task hiện tại.
- Không dùng `git reset --hard`, `git checkout -- <file>`, `git restore <file>`, `git clean -fd`, stash, hoặc xóa branch để dọn worktree nếu người dùng chưa yêu cầu chính xác thao tác đó.
- Không overwrite, format hoặc stage file không thuộc scope chỉ để làm status sạch.
- Nếu thay đổi của task chồng lên thay đổi có sẵn, dừng và báo conflict cụ thể; không tự chọn phiên bản.
- Không dùng `git add .` hoặc `git add -A` mặc định. Stage bằng đường dẫn cụ thể sau khi review diff.
- Sau khi stage, kiểm tra `git diff --cached --check` và `git diff --cached` trước commit.

## Branch model

```text
main  <- release PR từ dev
dev   <- integration/default branch
<type>/<issue-number>-<slug> <- feature/fix/docs branch từ dev
```

- Branch thông thường tạo từ `dev`, không từ `main`.
- Tên branch dùng lowercase kebab-case: `feat/42-product-filter`, `fix/57-cart-quantity`, `docs/12-agent-conventions`.
- `<type>` phải khớp intent chính và Conventional Commit type: `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `ci`, `perf`, `style`, `build`, `revert`.
- Một branch giải quyết một issue/slice tập trung. Không gom refactor hoặc cleanup không liên quan.
- Không push trực tiếp vào `main` hoặc `dev` trừ khi người dùng nêu rõ và repository policy cho phép.
- Không force-push. Không dùng `--force`; `--force-with-lease` cũng cần yêu cầu rõ vì vẫn rewrite remote history.

## Commit

Format:

```text
<type>(<scope>): <imperative summary>
```

Ví dụ:

```text
feat(storefront): add catalog gender filter
fix(admin): preserve inventory form values on conflict
refactor(api-sdk): centralize error envelope parsing
docs(agents): define git workflow conventions
test(schemas): cover invalid order transitions
```

- Summary dùng câu mệnh lệnh, cụ thể, không dấu chấm cuối; ưu tiên tối đa khoảng 72 ký tự khi hợp lý.
- Scope là app/package/domain bị ảnh hưởng (`storefront`, `admin`, `cms`, `api-sdk`, `schemas`, `ui`, `agents`); bỏ scope nếu thay đổi thực sự xuyên repository.
- Commit phải atomic: một behavior/refactor/docs unit có thể review và revert độc lập.
- Không trộn format toàn repo, generated output hoặc dependency update không liên quan vào commit feature.
- Body chỉ thêm khi cần giải thích “vì sao”, constraint, migration hoặc breaking behavior; không liệt kê lại diff.
- Breaking change dùng `!` và footer `BREAKING CHANGE:` khi thực sự thay đổi public contract.
- Commit message không được chứa tên AI tool, model, coding agent hoặc assistant, bao gồm nhưng không giới hạn: Claude, Anthropic, Codex, OpenAI, ChatGPT, Copilot, Gemini, Cursor, Windsurf, Perplexity, DeepSeek, Qwen, Grok, Llama và Mistral.
- Không thêm `Co-Authored-By`, `Generated-By`, `Assisted-By` hoặc attribution trực tiếp/gián tiếp cho AI, bot, agent hoặc assistant. Không diễn đạt vòng tránh như “AI-generated”, “generated by an assistant” hoặc “agent-assisted”.
- Hook `.husky/commit-msg` enforce danh sách tên phổ biến; convention vẫn áp dụng cho mọi tên agent khác dù chưa có trong regex.
- Không dùng `--no-verify` để bỏ qua hook. Nếu hook sai, sửa nguyên nhân hoặc báo blocker.
- Không amend commit của người dùng nếu chưa được yêu cầu. Khi được yêu cầu amend, xác nhận commit hiện tại thuộc task và chưa bị chia sẻ ngoài dự kiến.

## Staging và generated files

- Review `git diff -- <paths>` trước khi stage từng nhóm file liên quan.
- Stage source và test đi cùng behavior. Tài liệu/contract thay đổi cùng slice được stage cùng khi cần để commit tự đầy đủ.
- Không stage secret, `.env.local`, credential, token, build output, coverage, `.next`, `dist`, log hoặc scratch file.
- File generated chỉ commit nếu repository đang track và workflow yêu cầu. Không sửa thủ công `apps/*/src/routeTree.gen.ts`; chạy generator/build owner của file.
- Lockfile chỉ thay đổi cùng package manifest và phải phản ánh đúng package-manager command đã chạy. Không chỉnh lockfile thủ công.
- Nếu formatter thay đổi file ngoài scope, revert riêng phần formatting đó bằng edit an toàn; không dùng lệnh restore destructive lên file có thay đổi người dùng.

## Kiểm tra trước commit

1. `git status --short` — scope đúng, không có file lạ.
2. `git diff --check` — không whitespace error/conflict marker.
3. Chạy test hẹp cho behavior đã đổi.
4. Chạy lint/typecheck/test của workspace liên quan.
5. Chạy build khi đổi framework, routing, config, dependency hoặc production bundle.
6. Review `git diff` để tìm debug code, secret, TODO mơ hồ, generated noise và thay đổi ngoài scope.
7. Stage đường dẫn cụ thể; review lại `git diff --cached`.

Không tuyên bố commit “đã kiểm tra đầy đủ” nếu còn gate chưa chạy; liệt kê rõ gate bỏ qua và lý do.

## Rebase và merge

- Feature branch vào `dev`: ưu tiên squash merge theo `CONTRIBUTING.md`.
- `dev` vào `main`: release PR dùng regular merge để giữ các feature commit đã squash.
- Không merge `main` ngược vào feature chỉ để cập nhật nếu workflow dùng rebase; chọn chiến lược theo yêu cầu người dùng/repository và không trộn cả hai tùy tiện.
- Trước rebase, bảo đảm worktree sạch hoặc có kế hoạch bảo vệ thay đổi với sự đồng ý của người dùng.
- Khi resolve conflict, đọc cả hai phía và contract liên quan; không tự động chọn `ours`/`theirs` cho toàn bộ file.
- Sau rebase/conflict resolution, chạy lại test liên quan và kiểm tra không còn marker `<<<<<<<`, `=======`, `>>>>>>>`.

## Pull Request

- PR feature/fix target `dev`; chỉ release PR từ `dev` target `main`.
- PR title theo Conventional Commits và phải phản ánh thay đổi chính.
- Dùng `.github/PULL_REQUEST_TEMPLATE.md`; điền Summary, Test plan và Related issue.
- Liên kết issue bằng `Refs #N`; chỉ dùng `Closes #N` khi merge thực sự phải tự động đóng issue theo workflow.
- PR description nêu behavior, quyết định/constraint quan trọng, cách kiểm tra, screenshot cho UI và rủi ro/migration nếu có.
- PR title/body không được chứa bất kỳ tên AI tool, model, agent hoặc assistant nào và không được ghi attribution AI dưới mọi hình thức; CI kiểm tra danh sách tên phổ biến.
- Issue comment, PR comment, review comment, review summary, release note và GitHub discussion cũng không được nhắc tên agent/assistant hoặc mô tả nội dung do AI tạo. Chỉ mô tả thay đổi kỹ thuật, quyết định, bằng chứng kiểm thử và người chịu trách nhiệm thực tế.
- PR phải nhỏ, tập trung và có thể review. Nếu diff chứa nhiều concern độc lập, tách branch/PR trước khi mở.
- Không tự merge. Chỉ merge khi người dùng yêu cầu, CI xanh và target/strategy đúng.

## Issue và traceability

- Issue/PRD là nguồn scope delivery. Không âm thầm mở rộng acceptance criteria.
- Branch, commit và PR phải dùng cùng issue/domain vocabulary khi có thể.
- Triage dùng một nhãn phù hợp: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`.
- Type label phải khớp loại thay đổi (`type:feat`, `type:fix`, `type:docs`, ...).
- Không đổi label, close/reopen issue hoặc chỉnh milestone nếu chưa được yêu cầu.

## Recovery an toàn

- Khi commit sai nhưng chưa push: báo diff và đề xuất cách sửa; không reset/amend tự động.
- Khi đã push: ưu tiên commit sửa/revert có lịch sử rõ ràng; không rewrite history nếu chưa có đồng ý.
- Khi stage nhầm: dùng thao tác unstage không làm mất working-tree change và chỉ sau khi xác định đúng path.
- Trước mọi thao tác có thể mất dữ liệu hoặc rewrite history, nêu chính xác commit/branch/file bị ảnh hưởng và chờ xác nhận.
