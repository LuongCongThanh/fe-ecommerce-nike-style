# Contributing

This repo is maintained by a solo developer, currently not open to outside contributors. This doc exists so both the maintainer and any agent working in this repo follow the same GitHub conventions instead of improvising per session.

## Branch model

Two long-lived branches:

- **`main`** — stable. Only receives merges from `dev` via a Release PR.
- **`dev`** — active integration branch, **default branch** of the repo. All feature branches merge here first.

`master` is **frozen** (kept for historical reference only; nothing merges into it anymore).

Feature branches:

```text
<type>/<NN>-<slug>
```

`NN` is the task number in `docs/plan/tasks/` (omit it when there is no task). Example: `feat/9-storefront-catalog-browse`. Branch off `dev`, not `main`.

`<type>` matches the Conventional Commits type of the change (see below).

## Commits

[Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`, `ci:`, `perf:`, `style:`, `build:`, `revert:`), enforced by `commitlint` (`.husky/commit-msg`).

**Không nhắc tên AI/agent và không ghi AI attribution** trong Git history hoặc GitHub collaboration content. Commit message, branch description, PR title/body, review và Issue/PR comment không được chứa tên AI tool, model, coding agent hoặc assistant (ví dụ Claude, Codex, ChatGPT, Copilot, Gemini, Cursor), cũng không được thêm `Co-Authored-By` cho AI/bot/agent. Quy tắc áp dụng cho cả AI agent và người dùng, kể cả commit mới, amend, rebase hoặc squash merge. `.husky/commit-msg` chặn commit message và `Check PR title` CI kiểm tra PR title/body; comment/review được enforce bằng review policy. Không diễn đạt vòng tránh như “generated by an assistant” hoặc “AI-assisted”.

Before every commit, `.husky/pre-commit` runs `lint-staged`, `pnpm lint`, `pnpm typecheck` and `pnpm build` for the root app. Before every push, `.husky/pre-push` re-runs `pnpm typecheck` and `pnpm build`.

## Pull requests

- PR title also follows Conventional Commits (enforced by the `Check PR title` CI job) — under squash-merge, the PR title becomes the permanent commit message on `dev`.
- Use `.github/PULL_REQUEST_TEMPLATE.md` and fill in Type, Summary, Changes, Cách kiểm, Gap and Checklist. Name the related task folder (`docs/plan/tasks/<NN>-<name>`) when there is one.
- Target `dev` for regular feature/fix work. Target `main` only for a Release PR from `dev`.
- **Merge strategy**: squash-merge for feature branches into `dev`. Regular merge (not squash) for `dev` → `main` Release PRs, so each already-squashed feature commit stays visible in `main`'s history.
- Branch protection on `main` and `dev`: CI must pass before merging. No required reviewer approval (solo dev) — CI green is the merge gate.

## CI

`.github/workflows/ci.yml` runs Lint & format, OpenAPI contract regeneration, Typecheck, Unit tests and Production build on every PR and on push to `main`/`dev`. Builds use public placeholder URLs defined in the workflow; no production credentials are required. OpenAPI regeneration needs access to the pinned contract source. `pr-title-lint.yml` checks the PR title and attribution policy; `pr-body.yml` checks template sections.

## Development workflow

1. Read the task spec and current diff; continue unfinished work before starting another task. Interactive maintenance explicitly requested by the maintainer may proceed in the current checkout. Task runner eligibility still follows the task lifecycle.
2. Locate the owning module in [the structure guide](docs/architecture.md). Keep Next.js entry points in `app`, domain code in `features`, reusable UI in `shared`, and test support in `testing`.
3. Write or update the plan for task work. Make one coherent change; update imports, related docs and tests together when moving files.
4. Run focused checks first, then `pnpm lint`, `pnpm format:check`, `pnpm docs:check`, `pnpm typecheck`, `pnpm test` and `pnpm build` for source/config changes. Run affected E2E tests when browser behavior changes. For documentation-only work, run `pnpm docs:check`.
5. Review the diff and record checks and limitations. For a `ready-for-agent` task any agent commits, pushes, opens a PR to `dev` and squash-merges it once required checks pass; other work does so only when requested. Never merge into `main` outside a release PR.

Delete obsolete instructions once their replacement is linked from the documentation index. Preserve accepted decisions and useful task evidence; mark historical context explicitly. Do not remove fixtures, generated contracts or public assets solely because an import scan finds no reference.

## Tasks

Tasks are local Markdown files (`docs/plan/tasks/<NN>-<name>/spec.md`), not GitHub Issues. State is the `status` frontmatter field; see `docs/plan/README.md` and `docs/agents/issue-tracker.md`.
